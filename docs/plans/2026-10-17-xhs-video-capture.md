# Xiaohongshu video capture repair

User reports a video note was sent with only its cover. Supplied note ID: 6ab9d2d3000000000a027d7a. Browser control fails to initialize. Its public share URL returned HTML with generic feed initial state and no note/video fields; no real media download has been verified from that note.

Confirmed code gaps: normalizeXHS only reads video.media.stream and video.url; consumer.originVideoKey, mediaV2 and direct stream variants are missed. Cache entries are replaced wholesale when another response for the same ID arrives, so a cover-only summary can erase video URLs. Only one master URL is retained, with no retry using site-provided backup URLs. Sharing does not refresh the page's current initial state on demand.

Schema reference: independent primary implementations at https://github.com/JoeanAmier/XHS-Downloader/blob/master/source/application/video.py and https://github.com/ucmao/media-parser/blob/main/src/parsers/xiaohongshu_parser.py. They document originVideoKey's CDN mapping, mediaV2 and stream/backup fields. No third-party parsing service, cookies or account credentials will be used.

Steps: add failing regressions for each missing field, cache degradation and backup recovery; normalize one logical video with bounded allowlisted fallback URLs; merge same-ID records without losing media; request a fresh initial-state snapshot before extraction; try backup complete-video files when a source fails and preserve meaningful HTTP/size errors. Keep one video attachment, reject playlists/HTML, retain exact post identity and CDN limits. Build, test, review and commit; report the actual-site verification limit.

Validation: build succeeds and all 119 tests pass. Failing-first tests cover originVideoKey-only records, string mediaV2 plus direct stream backups, cover-summary cache degradation, on-demand state refresh before a blob-player share, a note-scoped HTML source fallback, recovery from an expired primary URL, rejecting partial range fragments, and nullable/malformed video fields without discarding image notes. Both network and isolated caches merge by exact note ID, and a route change during refresh rejects capture. CDN allowlists and attachment limits remain enforced for every candidate. Review found no blocking issues.

This fixes demonstrated parser/cache/download gaps but does not verify a successful media download for the supplied note. Its public HTML did not expose note details, and native browser control could not initialize. No content was sent to a real BOT. ## Follow-up after the user reproduced cover-only delivery

The user supplied the actual missing-media text: no per-video download failure, only “未获取到可下载的完整视频文件”, and the attachment list contains a cover plus JSON/Markdown. This locates the loss before the downloader, where the video list is empty. The user then supplied post-context.json confirming captureSource=network, hasVideo=true, attachedVideos=0, one attached image and no per-video download failures. The public-post API bridge worked; URL extraction is the failing stage.

Direct, unauthenticated inspection of Xiaohongshu's current public player bundles confirms that `video.media.stream.EF4` and string `video.mediaV2` containing `stream.EF4` are supported by the website but absent from our parser. Official source references: https://fe-static.xhscdn.com/formula-static/xhs-pc-web/public/resource/js/index.719e278e.js and https://fe-static.xhscdn.com/formula-static/xhs-pc-web/public/resource/js/async/xhs-web-player-mp4.41c672ed.js . These also map EF4/EF5/EF6/EF7 codec keys and handle proprietary encrypted `ef41`/`ef51`/`ef61` sample entries. Merely finding an MP4 `ftyp` header therefore cannot establish a usable attachment.

The repair recognizes current stream keys, re-reads the exact current note's public player props during sharing (without walking global stores or guessing which note a CDN request belongs to), and allows one second for the MAIN/isolated snapshot handshake. MP4 validation checks bounded box metadata, moov and mdat presence, and rejects encrypted sample entries before trying alternate source URLs. XHS video sharing now refuses to submit a cover-only packet when video capture/download fails, with distinct capture, download, and encrypted-only errors.

A self-generated 0.25-second H.264/AAC fixture (`test/fixtures/social-video.mp4`, verified with ffprobe) exercises normalization of current EF stream keys, downloading, material assembly, context packing, and attachment upload using simulated public media and BOT endpoints. The uploaded bytes must equal the entire fixture. Additional tests cover a missed first request, exact note-ID isolation, encrypted-source fallback, truncation rejection, and prevention of cover-only delivery. No real BOT request is issued.
